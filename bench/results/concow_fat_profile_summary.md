# B+Tree 并行瓶颈分析（2026-09-10）

## 方法与结果完整性

Mac ARM64、mimalloc、Apple clang，100,000 条记录、300,000 次已有 key 更新，4 个客户端，2 槽，GC 开启，无长读者，启用 parallel_materialization。
每组一次预热、三次新进程测量，交替配置顺序；均为中位数。构建结束后顺序运行测量，无同时编译或其它实验。

新增独立分析构建 `bench/concow_fat_profile`。普通构建模板参数 Profile=false，编译消除计时器的时钟读取和计数更新；保留固定大小的统计字段，不增加每节点开销。
计时对照 54 条、派发阈值对照 99 条，共 153 条测量全部通过最终参考 map 检查；GC pending_bytes=0，retired_bytes=reclaimed_bytes，appended+cow=updates。
计时构建与普通构建的总耗时中位数差异为 -2.1% 至 +5.7%，包括计时开销及运行噪声。因此分段数据用于定位，正式性能使用无计时构建。

每列独立取中位数，加之未计入的统计维护和客户端启动等时间，列和不必等于总耗时。

主要差异集中在并行轮；它包含通知 worker、调度、叶处理、原子任务领取和等待完成，不能把整段时间称为纯粹的线程唤醒开销。
例如 zipfian / 2 的 worker_loop_ns 总和仅约 27.28 ms，而并行轮墙钟累计 106.36 ms，支持频繁交接/等待显著的判断；二者时间定义不同，不能直接相减当作精确的调度开销。
热点下叶分组很小，多数由协调线程执行，但频繁发布消耗约 50 ms。发布计时包括 root/version 发布、争用输入锁和唤醒等待者，并未单独测锁争用。
规划和路径合并仍为串行工作，限制纯叶并行可以实现的端到端收益。

门槛按本轮不同叶的分组数计算，只有组数达到门槛才派给 worker 池。批次上限为 256，1048576 表示完全禁止池派发。

提高门槛能消除很多额外开销，但加速主要通过减少实际并行量取得，不能称为多 worker 扩展。完全禁用派发时，即使配置 2/4 workers，实际仍由协调线程执行；它与 workers=1 的小幅差异属于本轮噪声，不能作为并行更快的证据。

## 决定与下一步

保留实验控制器默认门槛 16 以维持旧对照，不凭单一 2 槽矩阵改动其它容量/模式的默认行为。
当前 B+Tree 的内存与性能基准优先采用 workers=1；研究并行可显式提高 parallel_min_groups，并同时报告实际派发比例。
本轮完成瓶颈定位和阈值实验，没有引入新的并发协议，也没有宣称获得真正多线程吞吐收益。

下一阶段可以推进 ART 适配：沿用按叶分组、快照发布和 GC，单独实现前缀分叉、节点扩容和共享路径合并；先确保正确，再验证叶处理成本是否足以摊薄并行交接。B+Tree 热点发布合并和协调线程参与并行工作属于后续独立优化，需另做版本/失败语义设计。

## 计时字段定义与复现

- queue_ns：协调线程等待输入、获得输入锁、复制批次的已完成区间。不是客户端 update 的累计等待时间。
- plan_ns：定位叶、分组和容量预留。
- inline_leaf_ns：协调线程直接执行叶组。
- parallel_wave_ns：派发到所有 worker 完成的整轮墙钟时间。
- merge_retire_ns：收集替换项、构造新路径、登记退休和转移所有权。
- publish_ns：发布一致快照、推进 committed、通知等待者，不包含回收。
- gc_ns：协调线程 publish 内的 try_reclaim，不包含外部 collect_garbage。
- serial_cow_ns：基线模式中的独占结构 COW，不含发布。
- worker_loop_ns：各 worker 任务领取与叶处理区间之和，与 parallel_wave_ns 重叠，不能计入协调线程阶段总和。
- worker_wakeups：进入已派发轮的 worker 次数，不是操作系统上下文切换次数。

统计读取使用原子快照。已提交末尾的回收/计时区间可能尚未结束，不保证与 benchmark elapsed 严格同边界；它们用于聚合阶段分析，不用于逐 ticket 延迟。
